# Бриф: tasker v0.1 — cross-scope deps + subtree-fetch + минимальный фронт

> **Адресат:** архитектор / owner **tasker** (репо tasker) · flow-require-pr
> **Заказчик:** workspace-архитектор (omnifield-hub)
> **Опора:** v0 ([[tasker-founding-vision]], модель уже стоит) — это **дельта** под догфуд-сид + «видеть дерево».
> **Цель этапа:** задать базу, чтобы дизайн (мост/chater) заносить **нодами и видеть**, а не специть вслепую.

## North star
Бэк — **максимус на текущий этап** (роадмап-дерево + кросс-скоуп зависимости), фронт — **минимальный read-first**
(видеть дерево, не красота). tasker становится durable-домом дизайна, где **роадмап продукта = своё дерево +
зависимости от чужих/инфра-узлов**.

## Часть A — Backend v0.1 (дельта к v0)

### A1. Cross-scope зависимости (важное — обсуждено)
Роадмап продукта зависит не только от своих веток, но и от **чужих** (shared/инфра-мехи типа моста = свой
workspace-дерево; продукт вешает cross-workspace-зависимость на инфра-узел).
- **Направленный `depends_on`** между узлами (можно как relation-kind `depends_on`, либо конвенция поверх
  существующего `blocks` — owner решает; главное — **однозначная направленность** «A зависит от B»).
  Cross-workspace — **уже поддержано** схемой (relations без ограничения на один ws) — подтвердить + тесты на
  cross-ws связь.
- **Обогащённый ответ relations:** для узла отдать входящие+исходящие связи с **workspace/key/title чужого
  узла + направление** — чтобы срез показал «заблокирован узлом `INFRA-42` (чужой)». (GET `/nodes/{key}/relations`
  расширить полями связанного узла; cross-ws явно.)
- Рёбра-зависимости **НЕ роллапятся** (роллап — внутри дерева parent/child; кросс — только relations).

### A2. Subtree-fetch (для рисовки дерева одним запросом)
- `GET /nodes/{key}/tree` (или `?depth=N`) → **узел + всё поддерево** (рекурсивно, обогащённые: статус, роллап,
  метки, кол-во детей). Один запрос вместо N. Для фронта и для догфуд-навигации.
- (по желанию) `GET /workspaces/{ws}/tree` → корни ws + поддеревья.

### A3. Догфуд-эргономика (минимум, по необходимости)
- Убедиться, что хватает для сида руками: create-node с parent (есть), reparent (PATCH parent_id — есть),
  create-relation cross-ws (есть). Если чего-то не хватит под сид Foundation-дерева — добить точечно.

## Часть B — Минимальный фронт (read-first, «видеть дерево»)
- `web/` воркспейс: vite+solid на **`@omnifield/vite-preset`** (`defineOmnifieldVite({plugins:[solid()]})` —
  base `/tasker/` из манифеста, ноль хардкода). API-клиент → **`/api/tasker`** (door-контракт), token-stub `Bearer`.
- **View (read-first):** список workspaces → дерево узлов (вложенность через subtree-fetch) + статус/роллап-бейдж
  + **кросс-деп рёбра** (показать «зависит от `WS-key` (чужой)»). Минимально: раскрытие узлов, без редактора.
  (Создание/правка — следующая итерация; сейчас смотрим.)
- **frontend-сервис** в `devbox.services.json` (vite, cwd web, port 5173, health) — как chater.
- `omnifield.yaml` front-route `/tasker`→5173 (уже есть).

## DoD (зона tasker)

## Handoff / после
- **→ workspace-архитектор:** после мержа — активация двери (recreate + regen), затем **догфуд-сид**
  (Foundation 0–6 + infra-workspace с узлом «universal-bridge» + дизайн chater — нодами, с cross-deps),
  затем гейты tasker. С наглядного дерева — предметный дизайн моста.

## North-star проверка
Кросс-деп без направленности/cross-ws (роадмап не видит чужие блокеры), нет subtree-fetch (фронт не нарисует
дерево), фронт-хардкод base (не пресет), или бэк раздут за «этап» — дефект. Максимус-на-этап, минимальный фронт.
